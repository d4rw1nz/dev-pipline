# 验证与复审

## 测试设计

测试从需求、公开接口、输入输出和失败条件出发，验证可观察行为。测试与生产代码按目录或语言标准测试目标分开存放。

先明确验收条件和检查范围，再设计用例、执行检查，核对原始输出与最终差异。测试发现问题时修正实现，保留原验收条件与有效断言。

## 覆盖率与行为验证

- 正式代码单测行覆盖率以 80% 为目标，优先覆盖本次新增、修改的核心模块，并报告整体情况。已有项目覆盖率偏低时，说明差距与本次范围。
- 报告工具、命令、统计范围和实际比例，支持时补充分支覆盖率。不同工具和平台的结果分别说明，只有口径一致时才合并。
- 说明生成代码、第三方依赖等排除项，保留自有业务代码的测试范围与有效断言。
- 未配置或工具不支持时标明未测量；本次范围内可配置则完成配置。低于目标时说明未覆盖职责与风险。
- 验收条件和关键行为已验证、风险与覆盖率缺口已说明时可以完成任务。项目另有明确覆盖率门槛时，按项目要求执行。
- 按功能选择失败与边界检查，如无效输入、权限拒绝、取消、重试、并发、部分成功、持久化恢复和资源释放。
- 时序测试使用可控条件表达先后顺序。测试名描述行为，失败信息应能定位实际问题。
- 单元测试验证规则，集成测试验证真实连接，目标环境验收验证部署行为。注明平台、版本、配置以及使用真实依赖还是替身。
- 分别记录通过、失败、跳过与未执行。定向检查通过时仍需说明完整命令的失败；性能结论区分实测结果与推断。

## 深度复审

正式代码完成首轮实现与验证后，执行 deep-review：重读同一需求的完整改动、相关 Git 历史、当前代码、调用方和测试。单独要求诊断性审查时可以直接开始，将缺失验证列为发现。

检查以下问题：

- 多轮修复是否造成重复规则、重复状态、额外服务实例或不断增长的特殊条件。
- 是否留下临时代码、死代码、旧格式兼容、无意义抽象、含义不明的常量或吞错逻辑。
- 依赖、状态写入与生命周期是否符合职责，界面是否复制业务规则。
- 时序、类型和资源管理是否依赖未验证的假设，是否增加不必要的开销。
- 测试是否覆盖原复现与重要失败，是否真正检查行为。

每项发现说明位置、触发条件、依据与影响。有明确收益时调整结构；未发现问题时说明检查范围和结果。

修正后运行受影响的测试、静态检查或构建，检查新增改动是否带来问题。必要验证通过、重要发现处理完毕后结束；尚未完成的关键验证如实保留。

## 交付内容整理

按 sanitize-artifacts 检查文档、界面文案、示例与 PR，使内容适合真实读者并可独立理解。

- 保留读者需要的事实、行为、技术理由、版本、限制与未验证项。
- 制作要求体现在内容与设计中；删除对话回顾、提示词和无关的实现过程说明。
- 区分正式范围与用于说明意图的示例，统一多轮修改后的用词、状态与叙述。
- 技术文档提供必要实现细节；产品界面只展示帮助用户理解和操作的信息。
- 核对模板内容、链接、来源和状态，替换占位说明与过时结论。

纯文档任务检查内容与引用即可。

## 交付前检查

按 [完成条件](workflow.md) 与 [交付检查](gates.md) 核对当前结果。相关代码或需求发生变化时重新验证受影响部分。

结果按 [保存规则](documentation.md#验证材料的保存) 简记在同一 Issue 或交付回复中，明确完成范围、限制与剩余工作。
