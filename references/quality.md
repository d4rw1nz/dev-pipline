# 验证、深度复审和交付内容

## 实现与测试分开

实现者负责生产行为和必要的局部自检；测试设计从需求、公开接口、输入输出和失败条件出发，不能把实现逐句改写成断言。测试与生产源码分目录或使用语言标准的独立测试目标。

是否创建 subagent 按 [子代理规则](../assets/AGENTS.md.template#子代理) 判断。跨模块、异步、持久化、协议变化或代码复杂本身不是启动理由，必须有四类场景之一的实际收益。测试独立设计不等于必须另起 agent；不符合条件时由主 agent 分阶段设计与执行。

符合条件时，先说明场景、具体收益、交付物和写入边界。以真并行为理由时，主 agent 必须同时推进其他不冲突的工作，不能只等待子任务；上下文隔离只返回结论、证据位置和必要摘录。分工方式：

1. 主 agent 先确定需求、验收标准、代码范围、测试入口和约定接口。
2. 实现 agent 修改生产代码；测试 agent 获得需求、公开行为、原始复现和环境限制，先设计用例，再读实现检查遗漏。不要只给实现摘要或要求测试接受当前输出。
3. 明确文件所有权，避免双方同时修改同一文件。测试 agent 可以提出生产问题，交由实现者修复；不能为让测试通过直接改需求或删除失败断言。
4. 接口尚未确定时先独立设计用例，确定后再接入测试；有先后依赖的工作不要强行并行。
5. 主 agent 检查实际测试文件、原始输出和最终 diff，合并后运行相关验证。子 agent 的“通过”描述不能代替执行证据。

未满足子代理条件时，主 agent 完成测试与自检，不因此标记交叉复审待完成。已确定必需的独立复审无法执行时，如实保留待完成；用户明确接受降级才按约定关闭，不虚构独立评审。创建用户侧新聊天不是测试分工的默认方式。

## 覆盖率目标与行为验证

- 正式代码单元测试行覆盖率尽量达到 80%，优先保证本次新增、修改的核心模块达到目标，并报告项目整体比例。已有项目明显低于目标时，保持本次范围，报告差距与后续方向，不擅自扩展成全仓补测。
- 同时报告覆盖率工具、命令、统计范围和原始摘要；有分支覆盖率时一起提供。不同测试工具和平台的数字不要未经换算直接相加。
- 生成代码、第三方依赖等排除项需说明。不能排除难测的自有业务代码、美化统计范围、用只执行不验证行为的测试或删除断言达标。
- 工具不支持或未配置覆盖率时如实报告“未测量”；在本次范围内可配置则配置，不猜测百分比。低于 80% 时解释未覆盖职责和实际风险，不自动把整项工作描述为全部验收完成。
- 80% 是改进目标，不是默认阻断门槛；本次验收条件和关键行为验证通过、相关风险与覆盖率缺口已说明时可以完成任务。项目若已有明确覆盖率门槛则遵守，不把“尽量达到”解释为跳过已有要求。
- 除正常路径外，验证实际相关的失败和边界：空输入、无效数据、权限拒绝、取消、重试、并发时序、部分成功、持久化恢复与资源释放。按功能选择，不机械地全部套用。
- 时序类测试使用可控条件表达先后顺序，避免仅靠固定睡眠制造“通过”。测试名描述可观察行为；失败时能够分辨实际问题。
- 单测替身验证规则，集成测试验证真实连接，目标环境验收验证部署后的行为。三者不能互相替代。平台、版本、配置、模型或服务是否真实都需注明。
- 记录通过、失败、跳过和未执行；某些定向测试通过不能掩盖完整命令失败。没有实测的性能改善只写推断，不能写成测量结论。

## deep-review：完成需求后的必经阶段

以下是正式代码交付前的复审；用户单独要求诊断性审查时可直接开始，把缺失验证列为发现，不以测试尚未通过拒绝审查。

首轮实现和验证结束后，重新读取同一需求的完整改动链路、相关 Git 历史、当前代码、调用方和测试，不只看最后一个补丁。需要专属 review 职责或独立审阅视角且有实际收益时，安排未编写该实现的 subagent 交叉复审；不能仅因属于正式代码就自动启动。使用干净上下文，只提供原始需求、源码、完整差异、原始验证证据与必要环境，不传入实现者的推理过程、预设结论或完整聊天历史。其余情况由主 agent 完成复审并如实注明自检。

检查以下实质问题：

- 多轮修复是否造成规则分叉、重复状态、隐式第二份服务或不断增长的特殊条件。
- 是否遗留临时代码、死代码、旧格式兼容、无意义抽象、魔法值和吞错逻辑。
- 依赖、状态写入和生命周期是否仍符合项目职责；界面是否复制了核心业务规则。
- 时序、类型与资源所有权是否依赖未证明的假设，是否增加了不必要的性能开销。
- 测试是否覆盖原复现与重要失败条件，是否在重复实现或绕开失败。

每项问题需要具体位置、触发条件、证据和影响。只有能减少真实复杂度、统一规则并提高可验证性时才重构。复审不是强制大改，没有问题就说明检查范围和结果。

修改后运行受影响的测试、静态检查或构建；复审引入新改动时检查它是否产生新问题，相关验证通过后结束，不无限循环做风格调整。无法完成关键验证时标明剩余工作，不用复审完成替代验收完成。

## sanitize-artifacts：让交付内容独立成立

提交文档、界面文案、报告、示例和 PR 前，按真实读者检查。对内容做三类判断：读者需要的信息；只用于指导制作的要求；偶然留下的聊天内容。只把第一类直接写入交付物。

- 删除或改写“按照你的要求”“上一轮改成”“为了满足提示词”等说明；约束通过实际设计体现。
- 用户举例仅用于说明意图时，不把例子误写成正式业务范围。
- 合并多轮修改形成的重复段落，统一术语、状态与叙述，不追加解释清理过程的文字。
- 必要的技术限制、版本、决策理由、已知风险和未执行验证必须保留。面向开发者的方案本来就需要实现细节，不能机械地全部删掉。
- 面向最终用户的页面不暴露构建工具、实现争论或与使用无关的排除项。
- 检查模板占位、过时链接、未注明来源的断言，以及只有看过聊天才懂的句子。

纯文档任务执行内容清理和链接、来源、状态检查；不虚构代码覆盖率或代码复审结果。

## 交付前检查

测试与复审须实际执行并核对原始输出；结果按 [验证材料的保存](documentation.md#验证材料的保存) 只记入已有 Issue 或交付回复。独立复审者返回发现与必要依据即可，不单独写报告，也不归档每轮执行输出。

按 [workflow 的任务类型与完成条件](workflow.md) 选择适用检查，再按 [gates](gates.md) 核对证据；不把正式代码检查套到纯文档或研究任务。检查与复审绑定当前输入版本，相关变动使旧结果失效。只报告实际完成的部分，明确未完成事项。
