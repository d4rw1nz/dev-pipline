# 任务执行与恢复

在明确范围内持续推进工作，记录当前结果与下一步。当前会话内连续执行；需要定时、监控或离线工作时，按用户要求使用宿主支持的自动化，并确定任务范围和停止条件。

## 完成条件

先明确交付类型、用户范围与授权。`run` 处理指定任务，`loop` 处理指定集合；混合任务分别判断完成情况。需要持续记录时使用 [Markdown Issue](issue-contract.md)。

| 任务类型 | 完成依据 |
| --- | --- |
| 研究、只读分析 | 约定问题已调查，来源、实际发现、适用范围、未知项与验证办法清楚；必要实验已执行 |
| 需求整理 | 同一 Issue 或需求文档保存明确范围、验收条件与待确认问题，必要来源可查 |
| 文档、知识维护 | 事实、职责、链接、来源和状态一致，内容可独立阅读 |
| 单独测试或审查 | 约定检查已执行，发现、限制、未执行项与依据已说明 |
| 原型交付 | 约定的实验问题已验证，结果、限制及删除或转正条件已说明 |
| 正式代码 | 验收满足，适用测试通过，深度复审及发现处置完成，文档一致 |

研究结论可以是不确定或不可行，审查结论可以是失败。需求草案中的待确认项仍需确认；原型验证与正式功能验收分别判断。任务完成、提交、推送、合并、发布和远端工单关闭各自记录实际状态。

所有交付按 [质量规则](quality.md) 整理内容，并按 [交付检查](gates.md) 核实结果。正式代码的覆盖率按质量规则报告；不适用的检查说明原因。任务结束时判断是否有可复用经验，有价值则更新已有规则或测试。

## 执行步骤

1. 读取已有任务、相关规则、模块说明与 Git 历史，确认工作区改动。历史缺失时注明判断依据的限制。
2. 查证未知事实，必要结论更新到 Issue 或同主题文档。实验用于定位与验证，关键选择只暂停依赖它的工作。
3. 按任务目标确定验收方法和实施步骤。已有需求直接引用，架构变化说明职责、历史与目标。
4. 实现约定行为，按 [验证与复审](quality.md) 从需求设计测试，记录真实结果。失败时返回根因分析。
5. 首轮验证后深度复审完整改动，核对历史、调用方和测试，记录有依据的发现。
6. 修正发现后重跑受影响检查，核实新增改动。相关检查通过、重要问题处理完毕后完成验收。
7. 精简 Issue 正文，更新头信息的 `status` 和 `updated`。按授权完成提交、推送或外部回写，并核实结果。
8. 按 [结果汇报](quality.md#结果汇报) 以图呈现实际改动，简要补充验证结果与剩余事项。

这些步骤按任务需要执行。开发步骤的进度写在当前情况中，Issue 状态统一维护在头信息里。

## 中断与恢复

`loop` 使用已确定的任务集合、优先级与依赖。新任务按用户指示加入。有实质进展、阻塞或下一步变化时改写原 Issue；集合全部完成后结束。用户暂停或剩余任务均受外部条件阻塞时，记录原因、下一步和恢复条件。

`resume` 重读 Issue、最新源码、工作区差异与相关来源：

- 范围内发生变化时，更新目标和下一步，重新验证受影响的结果，继续其余工作。
- 新增内容超出原授权时，仅推进已授权部分。用户已授权动态范围时按该约定执行。
- 范围记录不足时，从用户指令恢复；无法确认的部分保留待确认状态。

持续更新同一 Issue。可修复的失败继续处理；重复失败且没有新信息时调整诊断方法。约定的必需检查尚未完成时，保留具体缺口和下一步。

项目命令按 [Make 入口](make.md) 使用。远端尚未回写时继续本地工作，并在结果中简要说明。持续监控仅在用户要求时设置，通知集中于实质变化、失败或需要输入的事项。
