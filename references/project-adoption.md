# 分析与接入现有项目

从实际结构和历史形成可核实的当前结构，再确定目标职责。只要求分析时止于报告与计划；要求整理、迁移或完善时，在证据充分范围继续实施验证。

## 信息基线

读取规则、需求、结构、锁定依赖、生成方式、构建和 CI。沿真实入口追踪调用、数据、写入与生命周期，不仅看目录名。查看 Git 图及引入、改造、合并、回退、历史修复和关联 Issue/PR。检查当前未提交改动，建立相关测试基线，已有失败与未执行项单列。

区分语言/框架要求、生成结果、业务边界与历史摆放习惯。不能凭代码规模就拆服务、换框架，或擅自修完所有无关旧问题。

## 落地产物

- research：当前结构、关键调用/数据流、Git 证据、问题及未知事项。
- plans：目标职责、差异、保留/合并/拆分/删除对象、调用方与实施顺序。
- references/project-structure.md 或已有等价文档：实施后的实际目录与职责；目标不能冒充现状。
- 关联 Issue、需求和基线，后续验证结果记入 Issue，已有主题优先更新。

每个主要变化说明解决的实际问题。合理模块保留；有证据才调整结构。目标可以大胆，实施仍核实所有调用方及数据影响，不因迁移麻烦保留错误职责。

## 实施

按 [AGENTS.md 写入规则](documentation.md#agentsmd-写入) 将模板中的架构、Agent 和界面规则原文合入目标项目的 AGENTS.md，保留已有项目约定并避免重复；仅做只读分析时不写入。

先让工程可检查：Make 统一入口、复现测试、开发工具隔离。再按职责逐项调整调用、测试、文档和构建，删除失效路径，不长期并存两套规则。

每步一个可解释目的，保持可理解的 Git 历史；复杂并行任务必要时用 worktree，不覆盖未提交工作。每项变化运行适用验证并按 [quality](quality.md) 复审；需要独立审阅时再按子代理规则安排交叉复审。目录整齐不代表完成，需证明依赖、写入和生命周期符合目标。
