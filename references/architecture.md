# 架构判断与根因修复

架构调整以需求、代码事实和历史为依据。先确定合理的目标，再验证职责、调用方与数据影响，说明改动的收益和代价。

## 需求与约束

从四个问题开始：用户最终需要什么行为；哪些业务条件始终必须成立；谁拥有数据、写入权和生命周期；哪些约束由真实环境、产品承诺或外部协议决定。

区分实际约束与历史习惯。从当前需求重新判断目标结构，再决定旧实现中哪些部分仍有价值。

改变架构或风格前，至少核实相关需求、当前模块边界、依赖与调用方、状态写入路径、生命周期、现有测试以及工作区未提交改动。信息不足时查代码、找来源或做小实验，继续推进不受未知事项影响的工作。

同时查相关 Git 历史，特别是引入、重构、合并、回退和相同问题的历史修复；理解旧决定当时服务的需求和约束。将当时的决策理由与当前需求核对，具体方法见 [Git 规范](git.md)。

## 代码结构与职责

| 组织方式 | 应体现的架构责任 | 检查方式 |
| --- | --- | --- |
| 目录和模块 | 围绕业务能力或稳定职责组织 | 目录名能说明职责，相关修改集中在明确位置 |
| 导入和调用方向 | 依赖由组合入口指向功能和基础能力 | 核心规则不反向依赖界面；协议位置与使用范围一致，无循环依赖 |
| 数据和状态 | 每项状态有明确的写入职责 | 多个入口共享同一规则，状态保持一致 |
| 生命周期 | 谁创建，谁协调取消、释放和恢复 | 关闭、重试、切换会话后不会遗留无归属任务或隐式第二份实例 |
| 测试与执行入口 | 测试边界对应职责和可观察行为 | 业务规则可以独立验证，跨模块协议有集成验证 |
| 协作分工 | 人和 agent 的任务边界对应可独立检查的职责 | 减少同时编辑相同文件，接口与验收条件共享，责任不靠口头推断 |

优先沿用语言标准目录与成熟框架约定，根据实际职责决定模块划分。结构调整应解决重复规则或依赖问题，并通过行为验证确认。

## 界面与外部集成

优先使用公开接口，接入前核实版本和实际协议边界，避免重复实现已有能力。涉及界面时读取并执行 [AGENTS.md 模板中的界面规则](../assets/AGENTS.md.template#界面)，查目标平台的对应规范；借鉴其他项目前核实具体源码、适用条件与本项目差异，在本项目的目标环境中验证交互与实际行为。

## 根因修复

1. 明确期望与实际差异，保留最小复现或可靠证据。无法复现时说明观察范围与尚未证实的判断。
2. 在项目架构中定位相关功能：输入、业务规则、状态写入、异步任务、外部接口、展示及失败传播。查找其他调用方与同类实现，判断局部症状是否来自共享机制。
3. 检查不应该出现的状态为什么能够出现。结合重试、缓存、延时、默认对象和重复判断，查找异常产生的位置。
4. 提出根因与可证伪条件，通过测试、日志或小实验确认。先检查拥有该规则的模块，再考虑改调用方。
5. 在正确职责处修复，更新受影响调用方，删除旧绕行分支和废弃格式。没有证据的无关架构问题不混入本次修改。
6. 用原复现、失败条件、同类入口和必要边界验证，完成后进入 deep-review。

修复范围由根因决定：局部问题在所属模块处理，跨模块问题统一相关规则与调用方。验证应覆盖原问题和受影响的入口。

## 方向判断

有实质设计选择时，采用 geju 的方法审视目标与取舍，先给明确建议，再说明依据：

- **目标与把握程度**：建议的最终职责和行为；依据充分到什么程度，缺什么信息。
- **历史限制**：旧格式、旧名字和原有模块是否仍服务真实需求；未核实的约束不能直接删除。
- **打开思路**：至少采用一种有效检查，如从最终需求倒推、假设没有旧调用方、删除错误概念，或用增长场景检验薄弱处；增长假设应有实际需求依据。
- **具体调整**：明确保留、删除、合并、拆分的对象及受影响调用方。
- **方案选择**：当路径确有差异时比较“保留现状小改”“直接实现合理目标”“分步到达合理目标”，写清收益、成本并推荐一个。分步方案明确旧实现的移除条件。
- **首个验证点与反证**：先证明什么；出现什么结果需要改变建议；先识别不可逆的数据或外部变更。
- **代价与收益**：每项调整付出什么、消除哪个具体问题、何时可观察到收益。用实际行为或可测结果说明。

研究或方案任务交付建议与依据；已获实施授权且事实充分时继续实现和验证。
