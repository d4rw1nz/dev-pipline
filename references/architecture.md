# 架构判断与根因修复

本文件整合 geju 的方向判断：大胆提出更合理的目标，小心验证事实。它适用于架构选择、重复补丁和明显错误的职责安排，不要求每次小修改都展开完整方案报告。

## 第一性原理：先确定必须成立的事情

从四个问题开始：用户最终需要什么行为；哪些业务条件始终必须成立；谁拥有数据、写入权和生命周期；哪些约束由真实环境、产品承诺或外部协议决定。

把“旧代码这样写”“改起来麻烦”“之前建了这个目录”与真实约束分开。没有旧实现时会怎样设计，是用来发现错误假设的思考方式，不是重写整个项目的理由。

改变架构或风格前，至少核实相关需求、当前模块边界、依赖与调用方、状态写入路径、生命周期、现有测试以及工作区未提交改动。证据不足时读代码、找来源、做小实验；只阻止依赖未知信息的改动，其他明确工作继续进行。

同时查相关 Git 历史，特别是引入、重构、合并、回退和相同问题的历史修复；理解旧决定当时服务的需求和约束。用历史补足理由，再与当前事实核对，不能把过去正确的选择自动当成现在必须保留的结构。具体取证方式见 [Git 规范](git.md)。

## 组织即架构，架构即组织

| 组织方式 | 应体现的架构责任 | 检查方式 |
| --- | --- | --- |
| 目录和模块 | 围绕业务能力或稳定职责组织 | 目录名能解释职责，相关修改聚集在明确位置，不把不相关内容塞进万能目录 |
| 导入和调用方向 | 依赖由组合入口指向功能和基础能力 | 核心规则不反向依赖界面；协议位置与使用范围一致，无循环依赖 |
| 数据和状态 | 每项状态有明确的权威写入规则 | 不因多入口形成重复缓存、独立状态文件、双写或相互修正 |
| 生命周期 | 谁创建，谁协调取消、释放和恢复 | 关闭、重试、切换会话后不会遗留无归属任务或隐式第二份实例 |
| 测试与执行入口 | 测试边界对应职责和可观察行为 | 业务规则可以独立验证，跨模块协议有集成验证 |
| 协作分工 | 人和 agent 的任务边界对应可独立检查的职责 | 减少同时编辑相同文件，接口与验收条件共享，责任不靠口头推断 |

这是组织职责与代码结构的一致性要求，不是照搬公司部门表，也不是强制所有项目采用相同目录。简单模块不为形式拆层；语言标准目录和成熟框架约定优先。目录移动不能代替解决重复规则和错误依赖。

## 界面与外部集成

优先使用公开接口，接入前核实版本和实际协议边界，避免重复实现已有能力。涉及界面时读取并执行 [界面规则](interface.md)，查目标平台的对应规范；借鉴其他项目前核实具体源码、适用条件与本项目差异，在目标环境验证交互与实际行为，不能把参考项目已有能力当成本项目已经可用。

## bug 修复：先看整体关系，再确定改动范围

1. 明确期望与实际差异，保留最小复现或可靠证据。无法复现时说明观察范围，不编造确定根因。
2. 在项目架构中定位相关功能：输入、业务规则、状态写入、异步任务、外部接口、展示及失败传播。查找其他调用方与同类实现，判断局部症状是否来自共享机制。
3. 检查不应该出现的状态为什么能够出现。反复重试、额外缓存、延时、兜底对象、重复判断常是线索，不能把它们直接当最终方案。
4. 提出根因与可证伪条件，通过测试、日志或小实验确认。先检查拥有该规则的模块，再考虑改调用方。
5. 在正确职责处修复，更新受影响调用方，删除旧绕行分支和废弃格式。没有证据的无关架构问题不混入本次修改。
6. 用原复现、失败条件、同类入口和必要边界验证，完成后进入 deep-review。

架构视角要求理解完整关系，不要求扫描所有无关文件或扩大 diff。局部修复只有在确认根因确实局部、共享规则没有分叉时才成立；跨模块问题则不能为了少改文件继续在末端加条件。

## geju 方向判断

有实质设计选择时，先给明确建议，再提供证据：

- **目标与把握程度**：建议的最终职责和行为；依据充分到什么程度，缺什么信息。
- **历史限制**：旧格式、旧名字和原有模块是否仍服务真实需求；未核实的约束不能直接删除。
- **打开思路**：至少采用一种有效检查，如从最终需求倒推、假设没有旧调用方、删除错误概念，或用增长场景检验薄弱处；增长假设不能变成过度设计的理由。
- **具体调整**：明确保留、删除、合并、拆分的对象及受影响调用方。
- **方案选择**：当路径确有差异时比较“保留现状小改”“直接实现合理目标”“分步到达合理目标”，写清收益、成本并推荐一个。分步不意味着永久保留双实现。
- **首个验证点与反证**：先证明什么；出现什么结果需要改变建议；先识别不可逆的数据或外部变更。
- **代价与收益**：每项调整付出什么、消除哪个具体问题、何时可观察到收益。不要只写“更优雅”“更可维护”。

方向建议不是自动执行授权。用户请求仅为研究或方案时，交付可判断的方案与证据；已授权实现且证据充分时继续落实，无需反复确认常规设计选择。
