# Markdown Issue 记录

Issue 只用 Markdown 记录，直接读写文件。不要为此创建 CLI、数据库、JSON 状态、静态页面、搜索索引、同步服务或专用检查脚本。

## 何时记录

需要跨轮推进、中断恢复或后续跟进的任务，先查已有记录再更新或创建。普通问答、一次完成且无需跟进的小改，在交付回复中说明即可。长期偏好直接更新 AGENTS.md 或已有开发规范，不为记录偏好额外建 Issue。

默认一项任务一份 `docs/issues/<简短主题>.md`，已有 Markdown 任务目录则沿用。文件名保持稳定，同一问题继续修改原文件，不按日期、轮次、agent 或测试命令新建文件。不创建汇总所有任务的大文件、独立进度表或 Issue 索引；用文件名和 `rg` 查找，历史由 Git 保存。

## 写什么

只写当前任务用得上的内容，通常如下；没有内容的段落省略，不要求额外元数据或固定字段校验：

```markdown
# 任务标题

状态：进行中

## 目标
要解决的问题、范围，以及怎样算完成。已有需求文档时链接到对应内容。

## 当前情况
已完成的关键部分、仍存在的问题；阻塞时写清原因。

## 下一步
尚需执行的具体动作。

## 结果
实际改动、验证命令与结果、必要的代码版本和未验证项。
```

状态通常用待处理、进行中、阻塞、已完成。取消的任务注明取消原因，不标成已完成。实现、测试、复审是实际工作，不各设一层持久状态。

小任务的目标与验收直接写在 Issue 中，不另建需求和计划文件。已有需求或研究文档只链接，不复制正文；需要长期独立维护的产品说明才放入对应文档，Issue 留任务范围与引用。

## 控制篇幅

- 正文通常控制在 60 行以内。超过时先合并重复、删除过时内容；不能靠长行塞入大段文字，也不拆成更多过程文件来绕过限制。仍有必要的复杂内容可保留，以能准确继续工作为准，不机械截断。
- 每次更新改写原段落，替换已完成的下一步和过时判断，不追加“第几轮”“今日进展”或逐条命令流水账。未解决的问题与用户明确范围必须保留。
- 验证只留当前相关的命令、结果与限制；有 CI 记录直接链接。不嵌入原始日志、代码大段复制、diff、截图或聊天内容，不创建附件目录。具体见 [验证材料的保存](documentation.md#验证材料的保存)。
- 完成后删除已失效的计划、临时排查和已解决问题，通常压缩为 10–20 行的目标、结论、关键验证及必要链接。取消则留原因；有未完成承诺就保留，不伪装完成。
- 已结束文件留在原处，不搬入归档目录、不复制到完成清单、不追加周期总结。长期知识更新现有文档或测试，Issue 只留链接；没有新经验就不写反思段落。

## 使用与迁移

开工读当前 Issue 和相关代码；有实质变化时更新当前情况与下一步。结束时按 [完成条件](workflow.md) 核实结果后更新状态，不因 Markdown 写着“已完成”就跳过验证。恢复时核对最新需求和代码，过时结果不能代表当前实现。

外部任务只记录来源链接、必要的范围与当前结论，按 [来源规则](sources.md) 使用已有工具读取，不复制完整工单和评论，也不自动同步远端状态。

用户要求迁移已有 Issue 系统时，把仍需跟进的任务整理成 Markdown；已结束任务仅保留有实际参考价值的简短结论。移除原 JSON/数据库与 MD 双写、专用管理工具及其入口，修正引用，不把原记录整段转储成 Markdown。删除前核实未提交或无法重建的内容。普通开发不顺带迁移整个项目。
