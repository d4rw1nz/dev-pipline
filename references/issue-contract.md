# Markdown Issue 记录

一项任务一份 `docs/issues/<简短主题>.md`，直接读写文件。已有 Markdown 任务目录沿用原路径。标题、状态和更新时间放在 YAML 头信息中，正文保存任务内容。

## 何时记录

需要跨轮推进、中断恢复或后续跟进时，先查已有记录，再更新或创建。普通问答和无需跟进的小改在交付回复中说明；长期偏好直接更新 AGENTS.md 或已有开发规范。

文件名保持稳定，同一问题更新原文件。使用文件名、头信息和 `rg` 查找任务，历史通过 Git 查阅。Issue 的存储与维护限于这些 Markdown 文件，不另建管理工具、数据库、索引或同步服务。

## 文件格式

```markdown
---
title: 任务标题
status: 进行中
updated: "YYYY-MM-DD"
---

## 目标
要解决的问题、范围和完成条件。

## 当前情况
已完成的关键部分、仍存在的问题及阻塞原因。

## 下一步
尚需执行的具体动作。

## 结果
实际改动、验证命令与结果、必要的代码版本和未验证项。
```

头信息使用以下字段：

| 字段 | 用途 |
| --- | --- |
| `title` | 简短任务名称，正文省略重复标题 |
| `status` | 待处理、进行中、阻塞、已完成或已取消 |
| `updated` | 最近一次实质更新的日期，使用带引号的 `YYYY-MM-DD`；只读和纯格式整理不修改日期 |
| `created`（可选） | 已知的创建日期，格式同上，创建后保持不变 |
| `source`（可选） | 外部任务链接，多来源时使用列表 |
| `tags`（可选） | 少量有助于查找的模块或主题标签，使用列表 |

可选字段有实际内容才填写。状态、日期、来源和标签只在头信息中维护；正文按需要保留段落。验证记录和进度说明写在正文，头信息保持简短。

小任务的目标与验收直接写在 Issue 中。已有需求或研究文档只链接；需要长期独立维护的产品说明放入对应文档，Issue 保留本次范围与引用。

## 控制篇幅

- 整份文件通常控制在 60 行以内，使用正常段落与换行。超长时先合并重复、删除过时内容；保留准确恢复工作所需的范围与未解决问题，不靠长行或拆出过程文件压缩行数。
- 有实质变化时改写当前情况与下一步，替换过时判断和已完成动作。每个段落描述当前事实，历史留在 Git 中。
- 验证只留当前相关的命令、结果与限制，有 CI 记录直接链接。日志、截图、差异文件和调试脚本按 [保存规则](documentation.md#验证材料的保存) 临时处理。
- 完成后核实结果，再更新 `status` 和 `updated`，删除已失效的计划与排查过程。整份文件通常保留 10–20 行的头信息、目标、结论、关键验证与必要链接。取消时保留原因。
- 已结束文件留在原处，独立总表、归档副本和周期总结均不另建。可复用经验更新现有文档或测试，Issue 只留链接。

## 使用与迁移

开工读取当前 Issue 和相关代码；恢复时核对最新需求、来源与代码，重新验证受影响的结果。按 [完成条件](workflow.md) 验收后再标记完成；未完成的承诺继续保留。外部任务按 [来源规则](sources.md) 读取，远端回写遵守授权。

迁移已有 Issue 系统时，先保留未提交或无法重建的重要内容，再将待办整理为上述格式，已结束任务仅保留有参考价值的简短结论。随后移除旧存储、双写逻辑及专用管理入口，修正引用。迁移应在用户要求的项目范围内进行。
