# 项目文档

## 文档分工

| 位置 | 内容 |
| --- | --- |
| 根 README.md | 安装、开发、检查与运行方式，实际版本、依赖和配置示例 |
| 根 AGENTS.md | 项目约定、职责、开发入口与验证要求 |
| docs/README.md | 必要的分类和主题导航 |
| docs/requirements/ | 已确认范围、用户行为、验收条件与待确认问题 |
| docs/research/ | 源码事实、外部资料、技术限制与待验证判断 |
| docs/plans/ | 目标职责、方案取舍、实施顺序与验证方法 |
| docs/references/ | 来源、版本、源码入口及项目结构说明 |
| docs/issues/ | 带 YAML 头信息的任务记录，正文描述目标、当前情况、下一步和结果 |

按内容需要建立分类，优先更新已有主题。新增、移动或替换文档时修正引用；只有导航确有需要时才维护索引。Issue 使用 [记录规则](issue-contract.md) 中的头信息和文件名查找。

小任务的目标与验收直接写入 Issue；已有独立需求文档则引用原文。开发说明提供真实 Make 入口，长期规则能从 AGENTS.md 或现有导航找到。

## AGENTS.md 写入

执行 init、adopt 或明确要求同步规则时，读取 [AGENTS.md 模板](../assets/AGENTS.md.template)，将“架构”“Agent”“界面”三部分原文写入目标项目根目录的 AGENTS.md。普通开发与只读分析按现有规则工作。

- 固定规则保留原文、标题、编号和标点，实际写入目标文件。
- 新建文件时先写固定规则，再根据项目实际情况填写“项目开发约定”中的名称、路径、版本和命令。
- 已有文件保留项目职责、开发入口和验证要求，只补齐缺失内容。相同规则复用已有正文，较新的明确用户要求优先。
- 保留工具管理区块及其适用范围；需要补充的内容写在区块外，修改限于本次目标文件。
- 写入后核对完整规则、原有内容与差异，确保再次执行时不会重复追加。

## 写作与维护

- 先写结论，再给可复核的依据。技术内容注明必要的日期、状态与适用范围，仓库内使用相对链接；Issue 的通用信息统一放在头信息中。
- 分清需求确认、方案选择、代码实现与环境验证。源码与产品要求不一致时明确说明差异。
- 引用依赖或上游源码时记录版本、路径和查阅日期；引用本地源码时说明相关未提交改动。
- 一个结论维护一份正文，其余位置引用。方案替换后修正入口，保留仍有参考价值的历史说明。
- 文档应能独立阅读，保留技术理由、来源与限制。过程讨论留在会话中，正式内容按 [交付内容整理](quality.md#交付内容整理) 检查。
- 研究相邻仓库保持只读；实验使用隔离目录和测试身份，避免影响日常服务或接触真实凭据。

按文档用途选择内容：需求写行为与验收；研究写事实、来源和未知事项；计划写取舍、步骤和验证方法；资料写来源及适用条件。

## 验证材料的保存

验证与复审结果只记入已有 Issue 或交付回复。项目不建立或继续使用 validation/testing 文档目录，也不建立 evidence 附件目录。

- 记录必要的检查范围、代码版本、命令、结果、环境差异、未解决问题与未执行项。有 CI 结果时直接链接。
- 原始日志、覆盖率明细、截图、差异文件和调试脚本临时使用；需要文件时放系统临时目录，用完清理。正式构建产物沿用项目输出约定。
- 可复用验证方法写成测试或可执行检查，必要操作步骤补入现有开发说明；重要发现归入对应需求、研究或 Issue。
- 复测更新当前结果，保留影响后续判断的差异。验收依据是实际检查结果，原始输出和独立报告无需长期保存。
- 凭据、真实业务数据、依赖目录和大体积构建结果不进入文档或版本控制。

长期经验按 [知识维护](knowledge.md) 更新到对应位置。
