# 文档结构与知识沉淀

## 文档分工

| 位置 | 回答的问题 | 应包含的内容 |
| --- | --- | --- |
| 根 README.md | 怎样安装、开发、检查和运行 | 当前能力、准确版本、依赖安装、开发与生产构建、格式化与测试命令、配置占位值、docs 入口 |
| 根 AGENTS.md | 在这个项目怎样工作 | 稳定约定、职责边界、必要入口、禁止误用的事实和验证要求；长说明用链接 |
| docs/README.md | 去哪里找当前结论 | 分类入口、当前主题和状态；避免重复大段正文 |
| docs/requirements/ | 产品要做什么 | 已确认范围、用户行为、验收标准、待确认问题 |
| docs/research/ | 已经知道什么 | 源码事实、外部资料、技术限制、适用条件与待验证假设 |
| docs/plans/ | 为什么这样实现 | 目标职责、候选方案、决策依据、实施顺序、首个验证点及反证 |
| docs/references/ | 依据从哪里来 | 版本、固定提交、原始来源和源码入口；可放当前项目结构说明 |
| docs/issues/ 或项目现有权威存储 | 当前任务如何推进与恢复 | 稳定标识、来源、执行状态、验收与证据关联；由项目 CLI 维护 |

有内容时建立对应分类及其 README 索引；新增、移动、替换主题时同步索引与引用。纯小改优先更新已有主题，不机械地生成所有类别。

明确 init 可以建立基础分类索引，说明各类职责；不要预填虚构结论。需求文件唯一维护验收正文与稳定编号，Issue 引用需求版本、编号并保存执行结果，具体字段归属见 [Issue 契约](issue-contract.md)。文档中的确认/实现/验证状态描述各自事实，不另写第二份手动进度表。开发说明统一提供真实 Make 入口，项目长期反馈与经验应能从 AGENTS.md 或索引找到。

## AGENTS.md 写入

执行 init、adopt 或用户明确要求同步规则时，读取 [AGENTS.md 模板](../assets/AGENTS.md.template)，将其中“架构”“Agent”“界面”三部分完整写入目标项目根目录的 AGENTS.md。普通开发、只读分析和审查不自动同步。

- 三部分规则是固定正文，保留原文、分类标题、编号和标点；不能改写成摘要、只添加链接，或只更新 skill 自身。
- 新建 AGENTS.md 时，先写入这三部分，再根据项目实际情况填写模板中的“项目开发约定”。固定规则与需要填写的模板提示分开处理。
- 已有 AGENTS.md 时，保留项目职责、命令、验证要求和其他已有内容，只补齐缺失规则。同一条规则已有完整原文时复用，不重复追加；已有较新的明确用户要求优先。
- 保留工具管理区块及其适用范围。区块中已有相同原文时复用；需要补充的内容写在区块外，不覆盖工具管理内容。不自动修改子目录、其他组件或全局 AGENTS.md。
- 写入后读取目标文件，核对完整规则、项目原有内容和差异；只有目标 AGENTS.md 实际包含规则正文才算完成，重复执行不应产生重复内容。

## 记录规则

- 文档先写结论，再给证据；技术文档记录日期、状态和适用范围，仓库内使用相对链接。
- 分开描述“需求已确认”“方案已选择”“代码已实现”“某环境已验证”。这些状态不能相互替代。
- 当前源码事实与产品要求冲突时，分别记录并说明差异；不能为了贴合实现悄悄改需求。
- 引用依赖和上游源码时记录版本或固定提交、路径、查阅日期。引用本地源码还需说明是否含未提交改动及涉及范围；单独一个提交号不能代表脏工作区。
- 研究相邻仓库保持只读，不改日常服务、不读取或复制真实凭据；实验使用隔离目录和测试身份。
- 一个结论在一个位置维护，其他地方链接。正文维护细节，索引只写导航和简短状态，避免两处同时维护进度。
- 当前方案被替代时，旧文档标注“已被替代”并链接新文档，更新当前索引；保留有价值的历史证据，删除无用途的重复说明。
- 文档不依赖聊天上下文。技术决策保留可复核的事实与理由，不保存逐轮争论、提示词或原始思考过程。

## 精简写作格式

按内容选字段，不要求每篇套齐：

- 需求：日期与确认状态 → 用户行为与范围 → 可观察验收条件 → 待确认项 → 相关方案和验证。
- 研究：日期与源码基线 → 结论及适用条件 → 事实与来源 → 候选建议 → 未知和验证方法。
- 计划：日期与决策状态 → 目标与职责 → 依据和取舍 → 调整与删除对象 → 实施和验证顺序 → 反证。
- 资料：来源 → 版本与日期 → 使用的具体部分 → 本项目适用限制。

## 验证材料的保存

验证与复审结果只记入已有 Issue 或交付回复，不另建验证文档。不创建或继续向 `docs/validation/`、`docs/testing/` 及同类验证文档目录写入内容，也不把它们列入初始化或接入项目的目录结构。

- 普通测试与复审在已有 Issue 中保存简短结果：检查范围与代码版本、实际命令、退出码或结果、必要的环境差异、未解决问题与未执行项。有 CI 运行记录时直接引用，不复制其日志；没有 Issue 且不需要后续恢复的小改，在交付回复中说明即可。
- 原始日志、覆盖率明细、截图、diff/patch、输入摘要清单和调试脚本默认临时使用，需要文件时放系统临时目录，用完清理。不自动创建 `docs/issues/evidence/`、`docs/validation/evidence/` 或同类目录，也不把临时目录路径当作持久依据。
- 需要复用的验证方法优先写成测试代码或可执行检查；必要的环境、命令和操作步骤写入现有开发说明。重要发现归入对应需求、研究或 Issue，不另写验证报告。
- 用命令、回归测试、简短摘录或 CI 链接支持结论，不在仓库归档原始输出。凭据、真实业务数据、依赖目录和大体积构建结果不进入仓库。
- 复测更新当前结果，保留未解决问题和影响判断的关键差异，不追加逐轮流水账。门禁不得把存在独立报告或原始日志文件当作通过条件。

## 长期维护

经验的取舍、落点、召回与失效处理统一见 [知识维护](knowledge.md)。文档保存当前结论及依据，不追加逐轮聊天日志。

更新 AGENTS.md 时保留已有管理区块和适用范围，避免覆盖工具管理的内容。模板中的固定规则按上述要求原文写入；“项目开发约定”中的真实名称、路径、版本和命令须调查后填写，不能把待填写的提示留给使用者。
