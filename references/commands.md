# 入口与文件落地

使用 `$dev-pipline <操作> <目标或说明>`，也接受中文意图。操作由 skill 识别，不声称一个 SKILL.md 注册了多个原生斜杠命令。未指定操作时按意图选择，只有影响范围且无法判断时才问。

| 入口 | 行为与落地产物 |
| --- | --- |
| init | 新项目建立必要的 README、AGENTS.md、文档与 Make 入口；有实际任务才建立 Markdown Issue |
| adopt | 分析已有目录、调用、数据、构建和 Git 历史；落地当前结构、目标差异与计划，按授权实施 |
| research | 研究结论写入同主题文档；需持续跟进时用短 Issue 记录下一步，不复制研究正文 |
| require | 明确任务目标与验收，小任务直接写入 Issue，长期产品说明更新同一需求文档 |
| connect | 用已有工具读取指定外部任务，记录来源链接及必要结论 |
| run | 按任务类型完成指定工作，遵循 [闭环与完成条件](workflow.md) |
| loop | 自动处理一个已授权任务集合，按依赖推进，不擅自接管全部 backlog |
| test | 验证当前实现并保存结果，失败写回任务，不自动宣布完成 |
| review | deep-review，按子代理规则决定是否交叉复审，保存依据和发现；仅要求审查时不自行改代码 |
| resume | 重读持久记录、最新源码/来源/历史，核实旧证据再继续 |
| status | 只读真实进度，区分本地验收、远端状态、提交、合并、发布 |
| learn | 保存长期反馈或代码经验到适当位置，确认实际写入 |
| tidy | 原位精简重复和过时内容，压缩已结束 Issue，保留未解决问题，不另建归档或汇总文件 |

用户只要求研究、整理需求或审查时止于对应产物；要求“自动完成”时连续执行，无需逐阶段确认同一授权。

## init

先检查目录、Git、已有规则和工具。新项目按需建立需求、研究、设计、来源文档及职责索引，不建立验证文档目录；未定的选型写明未知，不编造命令或假目标。已有内容按职责补齐，不覆盖用户规则或生成文件。Issue 按 Markdown 规则直接记录，不生成管理工具、页面或专用 Make 入口。用户仅要求文档初始化时只完成该范围，如实注明其他能力未建立。

Makefile 基于实际工具，执行 help 与适用检查。AGENTS.md 按 [写入规则](documentation.md#agentsmd-写入) 包含模板中的完整架构、Agent 和界面规则，再简短导航到开发规范、结构、经验和 Issue 入口，不复制整套 skill。

## research 与 require

研究先明确问题、事实、假设，完成后更新结论、来源、版本、工作区状态和适用范围。负面结果保存，候选方案不自动变为需求。

需要记录的需求按明确表述区分已确认与待确认，更新同一 Issue 或需求文档。验收描述用户行为、正常结果、关键失败与边界，不强制编号或重复建文件。直接“实现 X”可确认 X 已明确部分，不重复要求批准；未确定产品选择不能自行确认。

外部任务保留来源链接，同一任务更新同一 Issue。需求变化时调整当前目标与受影响验收，不复制来源全文或把猜测写成用户意图。

## 示例

```text
$dev-pipline init 为这个项目建立开发体系
$dev-pipline adopt 分析现有结构并完善模块职责
$dev-pipline research 查清取消请求为什么仍更新页面
$dev-pipline require 支持断网后恢复上传
$dev-pipline connect 对接指定 GitHub 仓库的 Issue
$dev-pipline run docs/issues/upload-resume.md
$dev-pipline loop 完成指定的两项待办任务
$dev-pipline resume docs/issues/upload-resume.md
```

示例不表示项目已存在这些任务或外部连接。
